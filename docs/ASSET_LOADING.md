# 素材替换与加载规范

此规范自 r35 起适用于所有后续素材替换，以 r34 的加载优化为基线。GPT 原站为主版本，发布、验证后同步 GitHub。不要从其他平台的适配包覆盖正式工程。

## 主影片

- 保留作者最新原片的分辨率、帧率、全部编码画面和原声。不得为了首屏速度、设备判断或包体预算自动转码、降为 720p 或降帧。
- 统一运行 `node scripts/remux-film.mjs --source "新版原片.mp4" --segment-seconds 1`。只复制 H.264/AAC 数据为独立关键帧起始的 fMP4 分段；脚本逐包核对音视频内容、时间戳及统一偏移。其他编码需先明确无损兼容方案。
- `manifest.json` 必须记录实际源 SHA256、字节、时长、尺寸、帧率、编码、每段字节/时间/哈希和核对结果。缓存键与分段文件名随内容更新。不能复用旧片的体积、清晰度标签或旧缓存。
- 原片按 ≤16 MiB 分块保存在 `source-media/film-original/`，恢复时逐块及整片校验。发布包只带当前影片的一份播放分段；源码原片档案与旧影片不进入运行时包。单个运行时文件 ≤25 MiB，非主影片资源总计 ≤32 MB。不得以这些预算为由重新压缩原片。
- 影片在初始化开始即预载，开场不等待整片。片头提示后的开播门槛必须根据真实连续缓冲、实际分段体积和实测网络吞吐计算，显示真实进度，不能按时间伪造百分比。
- r37 起，原始 fMP4 先运行 `node scripts/group-film.mjs` 无损合并传输包，保留每个原始片段的时间、字节与哈希边界。GPT / 花生壳使用 ≤8 MiB 包；热铁盒派生版重新合并为 <5 MiB 包。比较合并前后整条 fMP4 字节序列 SHA256，禁止转码。当前 52 个原始片段合并为 GPT 的 12 个请求。
- 下载并发由清单 `delivery` 明确指定，默认兼容值为 2，GPT / 花生壳为 3，热铁盒可用 4；上限固定为 4，保持按时间顺序追加和有限原始数据前瞻。使用完整 VBR 字节曲线、至少 3 个实际网络样本、65% 保守吞吐、至少 10 秒已解码缓冲窗口与 7 秒抖动余量。缓存命中不能当成网络测速。播放后继续下载剩余内容。
- Cache API 按影片内容隔离，只清理本项目过期影片缓存。写入数量有界、存储失败或超时不阻塞播放。MSE 不可用或配额耗尽时，使用同一画质分段组成的 Blob；不能切低清版。
- 替换后检查舞台接点（当前 36 秒）、影片/舞台同源时钟、原声连续、seek、跳过和回看。时长改变时用 `--stage-at <秒数>` 明确新的接点，脚本会拒绝超出片长的接点；仍需实际检查尾段。不能让准备过程重置正在播放的时间。
- `scripts/prepare_film.py` 旧转码入口已停用压缩，统一转交上述无损脚本。

## Dot、三维网页与交互准备

- 模型、封面等后台资源共用有界低优先级队列，最多两个完整下载；主影片和实际交互保持优先。
- 数据可提前下载。冷场景构造不得在长按手势中阻塞主线程；直接返回先绘制遮罩，再准备场景。
- 保留 Dot 几何/材质计算的短时间片让出机制；纹理上传每个绘制间隔最多四张并受时间预算约束，最后一批也让出后再编译着色器。
- 依次完成舞台、卷轴、交接的着色器和首帧准备，恢复共享 renderer、rig 和 render target。准备不足时保持已有画面，不能露空场景。
- r37 必须在影片开始前完成舞台、卷轴、模型/封面解码及交接准备；从聊天稳定画面开始提前工作，耳机提示后同时等待真实媒体缓冲与场景准备。手动开播也遵守相同门槛。影片播放时不得再开始重型场景构建。
- 舞台预热采用真实显示尺寸，覆盖景深开启、反射和粒子阶段，不能只以小分辨率预热而把完整显存分配留给现场。白屏完成后改用常量白纹理，停止不可见的视频纹理上传；保留同一原片原声时钟。舞台期间不重复清理隐藏的卷轴画布。
- 抗锯齿不能依赖无上限增加画布采样。三维细边保持屏幕像素宽度并计算边缘覆盖率，倾斜卡片细边按投影补偿，保留现有自适应渲染预算。

## 卡片图片和参考视频

- 卡片封面独立于正文媒体，使用原图、异步解码和低请求优先级；在进入卷轴前完成实际封面的解码。不要把正文图片的临时地址写回封面。
- 未打开的正文仅保存 `data-media-src`，不下载其图片/视频；打开后仅激活阅读区域附近的素材，保留尺寸避免跳版。
- 所有卡片内视频默认并保持静音；原片与舞台的音量系统独立。
- 关闭时先保存收卡动画需要的封面，再暂停并释放正文视频及图片地址；重新打开仍可懒加载，并恢复有效的视频位置。封面不能被卸载或置空。

## 每次替换的验收

1. 源文件与档案整片 SHA256 一致；分段音视频包与原片一致，时间连续、比例和帧率正确。
2. 运行 `npm run check`、相关回归测试及 `npm run build`；检查发布文件清单只含当前影片和用到的素材。
3. 浏览器实际检查开场、主影片、Dot 舞台、卷轴、卡片开合/滚动/静音。影片或缓冲逻辑变化时做冷缓存限速播放和缓存复访，记录准备时长、再次缓冲及错误，不把缓存、单帧截图或构建成功当成完整播放验证。
4. 原片码率高于可用网络时必须真实缓冲，不能承诺任何网络都立即开播。说明测试网络、缓存和硬件边界。
   使用 `?diagnostics=1` 查看扣除隐藏解码预热后的实际掉帧、解码耗时、再次缓冲、播放期间长任务与场景就绪情况；测试报告须区分网络等待和呈现掉帧。阶段切换后使用原始音视频时钟，不能依赖已隐藏视频的帧回调继续触发。
5. Sites 源码每次推送 ≤64 MiB，大素材按 ≤32 MiB 的新增数据分批正常推送。中间提交不发布，最终发布包必须来自最后的完整源码树。GPT 原站发布并验证后，再同步同一提交到 GitHub。
